# 京东供应链与补货（自营供应商 · 12 仓场景）

> **场景前提**：我们是自营供应商，货入**京东全国仓**，用户下单后由京东仓发货。
> 「补货」= 往京东仓补我们的货。可用库存、在途、出库均以**京麦后台**数据为准。

---

## 一、先统一口径（每次补货前必看）

| 术语 | 含义 | 京麦取数位置 |
|---|---|---|
| **近7日出库** | 该仓最近 7 天发给用户的件数（= 京东真实动销） | 库存/报表 → 销售出库报表，按仓导出 |
| **可用库存** | 京东仓里当前可卖的我们的货 | 库存管理 → 各仓库存查询 |
| **采购未到货（在途）** | 已下单/在途、还没入仓的件数 | 采购单/入仓单列表 |
| **提前期 L** | 从补货指令到货到仓可售的天数（含在途运输+入库上架） | 按历史入仓单实测，通常 3–10 天 |

> ⚠️ 出库≠订单量。一单可能发多件，补货按**件数**算，不按订单数算。

---

## 二、补货公式（三层，从简到全）

### 第 1 层：基础版（现行公式，标准化）

```
补货量 = max(0, ceil( 近7日出库 ÷ 7 × 覆盖天数 − 可用库存 − 采购未到货 ))
```

- 现行覆盖天数 = **20 天**，本质是「把库存补到能卖 20 天的水平」。
- 向上取整（按箱/件的最小包装取整），结果不为负。
- **优点**：简单、三列数就能算，适合周例行。
- **盲点**：① 没区分供应提前期长短；② 没有应对销量波动的安全库存；③ 大促/季节波动没体现。

### 第 2 层：进阶版（日常推荐）

```
补货量 = max(0, ceil( 日均销 × (提前期 L + 覆盖天数) + 安全库存 − 可用库存 − 采购未到货 ))

其中：
  日均销     = 近7日出库 ÷ 7
  安全库存   = 日均销 × 波动天数（不会算波动就用 3–7 天）
```

- 提前期长的仓（远的慢仓、大促前物流紧）覆盖天数要相应拉长，否则补货在路上就断货。
- 安全库存是给"突然多卖"留的缓冲——爆款断一次货，前台权重和排名掉得比补货成本贵得多。

### 第 3 层：分层覆盖天数（不要全店一个 20）

按仓/按 SKU 分三层，而不是所有仓统一 20 天：

| 层级 | 判据（按仓按 SKU） | 覆盖天数 | 逻辑 |
|---|---|---|---|
| **A 爆款仓** | 日出库 ≥ 10 件 | **18–22 天** | 走量快、采销盯得紧，断供代价最大；提前期短可略压 |
| **B 常规仓** | 日出库 3–9 件 | **22–26 天** | 平衡断货与滞销 |
| **C 慢销仓/长尾 SKU** | 日出库 < 3 件 | **25–30 天** | 补货频次降下来，小批量多次，避免压仓 |

### 第 4 层：大促版（双 11 / 618）

```
大促补货量 = max(0, ceil( 日均销 × 大促系数 × (提前期 L + 覆盖天数) − 可用 − 在途 ))

大促系数：按去年同促销量 ÷ 平日销量估；无历史数据时保守取 2.5–3
覆盖天数：平时的 2–2.5 倍（大促物流慢+入仓排队）
```

**大促三条军规**：
1. **分 2–3 批入仓**——一批全押，卖爆了断货、卖不动了压死；首批 60% 提前入仓，二批 30% 促中前补，三批 10% 视动销补。
2. **入仓截止日倒排**——京东仓大促前会收紧入仓（一般提前 7–15 天截止），补货计划必须按**入仓截止日 − 提前期 L** 倒排下单日，不是按开卖日。
3. **滞销品不硬囤**——覆盖天数拉长只对动销品，C 层品大促照常小补。

## 三、滞销与缺货的权衡（公式背后的决策）

| 情况 | 判据 | 动作 |
|---|---|---|
| **滞销预警** | 可用库存 > 近 30 天出库（≈ 30 天卖不完） | 停止补货；报采销做活动/调拨消化；临期品优先处理 |
| **慢仓积压** | 某仓补货量算出来是 0 且库存高 | **优先走仓间调拨**（京麦调拨申请），比跨仓补货省运费也省入仓 |
| **断货风险** | 可用库存 < 日均销 × (L + 3) | 立即补，哪怕不够一箱也补；爆款断货掉权重 |
| **零出库** | 近 7 天出库 = 0 | 不补；先查是不是前台下架/无流量，再查是不是仓间缺货 |

**核心权衡**：覆盖天数每加 1 天，断货风险降一点、滞销和资金占用升一点。
自营的断货代价（前台不可售 + 采销考核 + 排名下滑）通常**高于**多压 5 天货的成本——所以偏保守，爆款宁多勿少。

## 四、偏仓治理与仓间调拨（多仓最值钱的一节）

**偏仓** = 同一个 SKU，有的仓压着卖不动、有的仓快断货。不治理就是"一边滞销一边缺货"，
全店总库存可能够，但结构是坏的。补货公式按仓单独算只能防"缺货"，治不了"偏仓"。

### 1. 偏仓检测（哪个仓滞销、滞销多少）

```
偏仓系数 = 该仓库存占比 ÷ 该仓销量占比（同 SKU 各仓之间比）
> 1.5  → 偏积压（库存占比明显高于销量占比）
< 0.67 → 偏缺货
```

同时用绝对量判据兜底：**可用库存 > 日均销 × 30 天 = 滞销**（30 天卖不完）。
输出时两个都要：偏仓系数定位"结构坏了"，绝对判据定位"压了多少件"。

### 2. 调拨量计算（滞销的调到要货的）

```
可调出量（供体仓） = max(0, 可用库存 − 本仓目标库存)   # 调完仍保留本仓正常周转含安全库存
需调入量（受体仓） = 该仓补货量
调拨量 = min(可调出量, 需调入量)，同大区优先配对
```

**调拨后必须修正补货量**：受体仓最终新补货量 = 原补货量 − 调入量——
调拨已经覆盖的部分**不再下采购单**，否则等于重复补货、反向压仓。

### 3. 调拨 vs 补货的决策

| 情形 | 选择 |
|---|---|
| 同 SKU 有积压仓 + 缺货仓 | **先调拨**：省入仓费、时效快（同大区 1–2 天 vs 补货 L 3–10 天） |
| 断货紧急（可用 < 日均×(L+3)）且只能跨大区调 | 调拨兜底**同时必须下补货单**——跨大区在途 2–4 天，等不起 |
| 积压仓调完只剩目标库存、无溢出 | 不调，受体仓直接补货 |
| 慢销长尾品偏仓 | 不值得调（调拨成本 > 货值），就地做活动消化或停补 |

### 4. 京麦调拨实操

- 入口：京麦 → 库存管理 → **仓间调拨/调拨申请**，选发出仓、收货仓、SKU、数量提交。
- **同大区优先**（华北/东北/华东/华中/华南/西南/西北），运费和时效都优；跨大区只在急用时用。
- 调拨在途也算"在途"——下次计算补货量时，调拨在途件要计入 `intransit`，否则又会重补。
- 调拨前确认接收仓的**收货能力**（大促前仓忙，调拨单可能压着不入库）。

### 5. 脚本一键出偏仓报告

```bash
python3 "$SKILL_DIR/scripts/calc_restock.py" restock.csv --cover-by-tier
```

输出三段：**偏仓检测**（积压/缺货仓及占比比值）→ **调拨建议**（从哪仓调到哪仓、多少件、依据）
→ **调拨后最终补货量**（修正各仓采购单）。`--no-transfer` 可关闭；`--json` 供程序取用。

**示例**（实测输出）：

```
偏仓检测：
  📦 100038874722 / 沈阳仓：库存占 51.3% vs 销量占 6.7%（比值 7.69）→ 偏积压
  🕳 100038874722 / 广州仓：库存占 10.3% vs 销量占 30.0%（比值 0.34）→ 偏缺货
  → 同一 SKU 同时出现积压仓与缺货仓 = 典型偏仓，优先调拨而非补货

仓间调拨建议：
  100038874722  沈阳仓 → 广州仓  136 件

  注意：跨大区在途2-4天；⚠️断货紧急，调拨兜底同时必须下补货单

调拨后最终新补货量：
  100038874722 / 广州仓：248 → 112（调入 136）
```

## 五、B 仓（中心/分拨仓）两级供应链

货物流变成**供应商 → B 仓 → 全国 C 仓**后，补货从"一层"变"两层"：
B 仓不再是简单的"又一个仓"，它是**蓄水池 + 分拨枢纽**。算错 B 仓，
要么全链路压货（B 仓囤多了），要么所有 C 仓一起断（B 仓见底）——
比单个 C 仓出问题的后果严重一个量级。

### 1. 两层公式

**C 仓层（公式不变，但"在途"口径变了）**：

```
C仓补货量 = max(0, ceil( 日均_C × (L_BC + 覆盖天数) + 安全库存_C − 可用_C − 在途_B→C ))
```

`在途` = **已从 B 仓发出、还没到 C 仓**的量（不再是供应商→仓的在途）。
调拨在途件同样计入，否则会重补。

**B 仓层（新增，向供应商/工厂下单的依据）**：

```
B仓目标库存 = Σ_i[ 日均_i × (L_B + L_BC + 覆盖天数_i) ] + B仓安全库存
B仓补货量   = max(0, B仓目标库存 − B仓可用 − 在途_供应商→B)

L_B  = 供应商→B 仓提前期（生产+运输+入库）
L_BC = B 仓→C 仓在途天数（同大区 1–2 天，跨大区 2–4 天）
```

**关键在时间三段叠加**：B 仓的货要同时覆盖"到 B 仓的时间(L_B) + B 到 C 的时间(L_BC) + C 仓自己的覆盖天数"。
B 仓备的不是今天的缺口，是**未来 L_B 天后 C 仓们的缺口**。

### 2. B 仓安全库存：聚集效应（风险池）

各 C 仓各自持安全库存，波动会被放大；**B 仓集中持有，波动互相抵消**：

```
σ_总 ≈ √(Σ σ_i²)   <   Σ σ_i      （各仓需求不完全相关时）
```

实用简化：**B 仓安全库存 = 全网日均 × 5–7 天**，
明显小于"各 C 仓安全库存之和"——这就是两级供应链相对单层省库存的地方。
C 仓端可以因此把安全库存降到 3 天甚至更低，让 B 仓扛波动。

### 3. B 仓直拨优先于 C 仓互调

调拨/补货的源头优先级：

| 优先级 | 方式 | 时效 | 说明 |
|---|---|---|---|
| 1 | **B 仓直拨** | L_BC（1–4 天） | 源头发货、链路最短、不用求别的供应商仓 |
| 2 | C 仓间互调 | 同大区 1–2 天 | B 仓也没溢出时用 |
| 3 | 向供应商紧急采购 | L_B | 最慢，大促前慎用 |

**B 仓直拨的两个规则**：
- B 仓拨出量不能把 B 仓掏空——保留 `全网日均 × (L_B + L_BC + 3 天)` 的周转量，其余才可拨。
- **B 仓拨出多少，B 仓采购量就要补回多少**（脚本自动算），否则 B 仓被悄悄掏空，下次全链路断供。

### 4. B 仓的两个极端风险（比 C 仓严重）

| 情形 | 判据 | 后果 |
|---|---|---|
| **B 仓压货** | B 仓可用 > 全网日均 × 30 天 | 全链路滞销 + 资金占用，还可能产生仓储费 |
| **B 仓断供** | B 仓可用 < 全网日均 × (L_B + L_BC + 3) | **所有 C 仓一起断**，前台全SKU不可售，采销层面的大事故 |

B 仓见底比 C 仓见底危险得多——**B 仓的覆盖天数要偏保守**（宁多勿少），
C 仓反而可以薄库存（有 B 仓兜底）。

### 5. 实操要点（京麦）

- **入 B 仓**：供应商送货或调拨入 B 仓；B 仓入库时效长，下单要按 L_B 倒排。
- **B→C 调拨**：京麦调拨申请，发出仓选 B 仓；调拨在途计入 C 仓 `intransit`。
- **B 仓组套/拆零**：若组合装在 B 仓组套，B 仓库存 = 成品 + 原料 + 在制，安全库存要另加组套批量损耗。
- **大促**：B 仓提前入仓（大促前仓紧，B 仓也排队）；首批直接入 B 仓再分拨，比直发 C 仓更稳。

### 6. B 仓模式的限制（用之前必读，2026-10-15 补）

- 脚本**默认单层模式**；只有传 `--b-warehouse B仓` 才切两级。CSV 里 B 仓必须占一行且 `out7` 填 0——它的"出库"是发给 C 仓的量，计入会重复。
- `L_B`（供应商→B）与 `L_BC`（B→C）默认 7/2 天只是**占位值**，须按历史入仓单实测替换；B 仓断供 = 所有 C 仓一起断，参数拍脑袋的代价比单层模式大一个量级。
- 多 SKU 时**每个 SKU 的 B 仓单独算**，不混别家 SKU 的 C 仓需求。
- 大促"首批直接入 B 仓再分拨"只在 B 仓作业能力够时用；组套/拆零的 B 仓库存 = 成品 + 原料 + 在制，安全库存要另加组套批量损耗。
- B 仓模式下 C 仓可薄库存（有 B 仓兜底），但 **B 仓自身的覆盖天数要偏保守**（宁多勿少）。

### 7. 脚本用法（B 仓模式）

```bash
python3 "$SKILL_DIR/scripts/calc_restock.py" restock.csv \
    --b-warehouse B仓 --lead 7 --lead-bc 2 --cover-by-tier
```

- CSV 里 B 仓也占一行（`warehouse=B仓`，`out7` 填 0——它的出库是发给 C 仓的量，计入会重复）
- 输出新增 **B 仓补货建议**段：目标库存拆解（C 仓需求 + 安全库存）+ 最终向供应商采购量（含直拨补回）
- 调拨建议自动优先走 B 仓直拨，方式列标注「B仓直拨 / C仓互调」

**实测示例**（B 仓 900 件、4 个 C 仓、全网日均 30）：

```
B 仓补货建议：目标库存 = C仓需求 870 + B仓安全库存 150 = 1020
             现有 900 → 向供应商采购 720 件（其中 600 件是直拨给 C 仓的补回量）
调拨建议：B仓 → 广州仓 248 件（B仓直拨，断货紧急优先安排）
          B仓 → 上海仓 194 件（B仓直拨）
          沈阳仓 → 北京仓 46 件（C仓互调，跨大区）
```

## 六、周例行补货 SOP（固定动作，每周一次）

1. **导三张表**（同一天，保证口径一致）：
   - 近 7 天各仓出库明细（SKU × 仓）
   - 当前各仓可用库存（SKU × 仓）
   - 在途/采购未到货（SKU × 仓）
2. **对齐 SKU 编码**：三张表的 SKU 命名/编码可能不一致，先用商品编码对齐再合并。
3. **套公式算补货量**（按 SKU × 仓逐行；用 `scripts/calc_restock.py` 批量算）。
4. **过一遍异常清单**：补货量为 0 的、滞销预警的、在途但库存为 0 的。
5. **输出 Excel 多 Sheet**（沿用用户既有模板，**不改表头，只填结果列**）：

| Sheet | 内容 |
|---|---|
| 仓库汇总 | 每个仓的补货总件数、涉及 SKU 数、总金额（可选） |
| 补货明细 | SKU × 仓 的补货量、公式中间值（日均销/可用/在途） |
| 滞销与调拨建议 | 滞销 SKU、建议调拨的仓对、暂停补货清单 |

6. **提交**：京麦补货/采购单按明细下单，在途数量回写（下次计算的"采购未到货"就有了）。

## 七、下单前检查清单（每个采购单必查，2026-10-15 补）

补货量算完 ≠ 可以直接下单。提交采购单/调拨单前逐项过：

| 检查 | 动作 | 不查的后果 |
|---|---|---|
| **箱规 / 起订量** | 补货量向上取整到箱规整数倍；不够一箱按起订量补或并入下批 | 下了 37 件供应商不发货/加价，账实不符 |
| **临期 / 保质期** | 在库+在途批次的保质期剩余必须 > 覆盖天数 + L；临期品（剩余覆盖不完）**不补**，报采销做活动/调拨消化 | 补回去的货还没卖完就临期，退仓都来不及 |
| **在途口径** | 采购在途 + 调拨在途 + B→C 在途**全部计入**再算净需求 | 重复下单，货到爆仓、滞销 |
| **缺货紧急度** | 可用 < 日均×(L+3) 的仓标"紧急"，优先走 B 仓直拨/调拨，采购单只是兜底 | 等采购到了，前台权重已断 |
| **入仓截止** | 大促/活动期按「入仓截止日 − L」倒排下单日，不是按开卖日 | 货卖爆了货还在路上 |
| **责任人 / 复核** | 谁下单、哪天跟踪到仓、异常谁处理——补货是闭环，不是算完就完 | 在途单没人跟， silently 延误 |

```bash
python3 "$SKILL_DIR/scripts/calc_restock.py" restock.csv --out 补货结果.csv
```

- 默认参数就是第 2 层进阶版：`--cover 20 --safety-days 5 --lead 7`
- 输出：每行补货量（向上取整、不低于 0）+ 按仓汇总 + 滞销标记 + JSON/CSV
- 分层覆盖天数可用 `--cover-by-tier` 自动按日出库分 A/B/C 层套不同天数
- **输入纪律**：out7/stock/intransit 出现非数字（如"未知"）时脚本报出行号/SKU/仓/字段并**退出码 2 拒绝计算**——不把异常值静默当 0（那会产生错误采购量）；回导出表修正该单元格再跑
- **多 SKU + B 仓**：`--b-warehouse B仓` 时每个 SKU 的 B 仓单独按本 SKU 的 C 仓需求计算，互不混算

**输入 CSV 示例**：

```csv
sku,warehouse,out7,stock,intransit
100038874722,北京仓,84,120,60
100038874722,广州仓,63,40,0
100017283385,上海仓,7,55,0
```

## 九、常见错误（都犯过，列出来防再犯）

| 错误 | 后果 |
|---|---|
| 用**订单数**当出库量 | 一单多件时少补一半以上 |
| 用**全国汇总**算补货量再平分到仓 | 爆量仓断货、慢仓压货——必须按仓单独算 |
| 忘了减**采购未到货** | 重复下单，货到仓爆仓、滞销 |
| 覆盖天数全店统一 | 慢销品压死、爆款断供 |
| 大促按开卖日倒排 | 没算入仓截止日和排队，货卖爆了货还在路上 |
| 出库数据跨月/含退货未剔 | 退货拉高出库假象，取数要确认是净出库 |
| 补货量没按箱规取整、没查临期就下单 | 供应商不发货/货补回去就临期，白占资金（下单前检查清单见第七节） |
